# 06 · 规划与控制：业界参考

> 写给：已经在本仓库实现「Frenet 横纵解耦（`paths.ts` + `speed.ts`）+ 收敛迭代 + 走廊族 + 跟驰」的你。
> 这份文档解决三个具体问题：**你的架构在业界叫什么、缺哪一层、以及你刚踩过的"责任划分"坑业界怎么防**。
> 所有链接都已逐条核实可达（2026-09-27，HTTP 200），无法核实的已删除或标注。

## ① 这套东西解决什么问题

你现在的规划器：Frenet 参考线 → `vCap` → **路径层 × 速度上限的收敛迭代（≤3 轮）** → ST 速度层 → 合成轨迹。
这套形状就是业界的 **EM Planner**（横向-纵向解耦 + 迭代），你已经独立走到了同一个位置——所以你读业界资料时
应该问的不是"我该改成什么架构"，而是"**我缺的那几层分别解决什么问题**"。按你当前的实际痛点排序，缺的是：
① **预测层**（没有它，所有会动的车都只能按"静止障碍"规划——这是你"60~100m 处提前重刹"的根因）；
② **责任划分独立于几何**（你为"旁边车道的车要不要管"折腾了两轮，最后靠修投影才缓解）；
③ **安全兜底独立于规划**（你的 `EMERGENCY` 长在规划器里，业界把它放在控制层）。

## ④ 关键机制 / 公式 / 数据结构

### 4.1 横纵解耦为什么必须迭代

路径层需要速度（横向机动距离随速度增长、走廊膨胀量 `marginFor(v)` 也随速度变），速度层需要路径（几何决定曲率与可行速度）。
两者互为输入 ⇒ 要么固定点迭代，要么联合优化。你的做法：`vAssume` 从 `max(当前速度, 慢行档)` 起，
每轮用 `margin(vAssume)` 求路径、再由路径几何反推速度上限 `u`，**≤3 轮 + 提前停止（变化不降反增就停）**。
EM Planner 论文与 `Class_Architecture_Planning` 里的 "interweave" 是同一件事。
**要守的两条**：① 迭代必须有**收敛判据**（你用的是 0.2m / 0.5 m·s⁻¹，并统计">1 轮的帧占比"——这个指标很专业 ✓）；
② 迭代的初值与下界不能自锁（你已经踩过并解决："停车 → 裕度最大 → 封死 → 永不起步"，解法是把几何评估速度下限设为慢行档）。

### 4.2 SL 路径层：五次多项式与横向约束

横向用五次多项式（位置、速度、加速度两端各三个边界条件，共 6 个 ⇒ 5 次唯一）：
`l(s) = a0 + a1 s + a2 s² + a3 s³ + a4 s⁴ + a5 s⁵`，两端给定 `(l, l', l'')`。
完成一次横向机动 `|Δl|` 的最短纵向距离与速度的关系：
- 设机动时间 `T`，则横向加速度峰值 ∝ `|Δl|/T²`，要求 ≤ `A_LAT_MAX` ⇒ `T ∝ √(|Δl| / A_LAT_MAX)`；
- 机动期间车前进 `S = v·T` ⇒ **`S_min ∝ v·√(|Δl| / A_LAT_MAX)`**。

你的 `paths.ts` 里 `S_min = √(5.77 · |Δl| · v² / A_LAT_MAX)` 正是这个形式（`5.77` 是五次多项式剖面的常数因子）。
**关键在于它对 `v` 是线性的、对 `A_LAT_MAX` 是 `1/√` 的**：所以高速时横向机动"来不及"是数学必然，不是调参问题——
这也解释了为什么"限幅让位候选"在低速度域才容易赢。

### 4.3 ST 速度层：S-T 图、条目语义与"静态障碍假设"

Apollo 的 ST 图做法：把路径上所有障碍投成 **S-T 上的禁区**（障碍占据的 `s` 区间 × 占据的时间区间），
然后在该图上求满足单调/速度上下界/接缝光滑的五次样条剖面。
**你的 `STObstacle {sMin,sMax,tMin,tMax}` 是同一件事的二维简化版**，而**"把障碍当静态"在公式上就等于 `tMax = ∞`**
（障碍永久占据该 `s` 区间）。这对静态障碍**恰好正确**，对会动的车则是最坏假设 ⇒ 你观察到的
"60~100m 处提前重刹"（先按停车线规划）在数学上就来自这里。
`tMax = ∞` 的三个后果：① 目标函数里没有任何"它会走开"的信息；② 跟驰只能靠额外的 `follow` 分支打补丁（你已经做了）；
③ 安全门（"能不能停住"）会误杀跟驰（你已经发现并改成"能不能降到前车速度"）。
**正解**：给 ST 条目一个**预测的 `tMax`**（哪怕只是常速度外推），让"它会走开"进入优化，而不是在优化之外打补丁。

### 4.4 责任划分：为什么必须独立于几何

RSS 的核心思路：把"谁该让谁"写成**不依赖具体几何形状**的规则 + 解析的安全距离。纵向安全距离的**结构**是：
```
d_min ≈ 后车在响应时间 ρ 内的位移 + 后车最大加速带来的额外距离 + 后车制动所需距离 − 前车制动能"让出"的距离
       = v_r·ρ + ½·a_max·ρ² + (v_r + ρ·a_max)² / (2·b_min) − v_f² / (2·b_max)
```
（`v_r` 后车速度、`v_f` 前车速度、`a_max` 后车最大加速度、`b_min` 后车最小制动、`b_max` 前车最大制动；
**精确形式与不对称修正以论文 §3 为准**。）
它给你的三条启示，正好对着你踩过的坑：
1. **"该不该让"由规则与路权决定，不由几何膨胀决定**。"相邻车道的车在它的车道里 ⇒ 我没有让行义务"是一条**规则**；
   你之前让走廊膨胀去隐式表达它，于是"投影误差 1m"就变成了"我必须横移"。
2. **规则要看"能力"而不是"保守常数"**：`b_min`/`a_max` 是**车辆自己的**参数。
   你的可达性闸门用 `car.acceleration`（而不是规划侧的保守 `A_BRAKE`）已经是这个思想的正确形态 ✓。
3. **让行是有条件的、可判定的**（切入时责任转移），而不是"离我近就让"。

### 4.5 分层安全兜底

工业界的层次（对照你自己的层次）：

| 层 | 职责 | 你仓库里的位置 |
|---|---|---|
| 规划（舒适） | 光滑、舒适、遵守规则 | `planner.ts` + `paths.ts`/`speed.ts` ✓ |
| 安全门（规则/包络） | 判定"这个动作合不合法" | `marginFor(v)` 标定表 + 可达性闸门（部分具备 ✓） |
| 紧急制动（AEB） | 最后兜底，可覆盖规划 | `EMERGENCY` 状态（**在规划器内 ✗**，业界在控制层独立节点） |
| 故障守护（Guardian） | 模块/硬件异常 → 停车 | **无**（`detector.ts` 只是离线检查器） |

**为什么"能不能停住"要问车辆自身能力**：安全门如果用规划侧的保守常数（你的 `A_BRAKE`），
就会出现"规划器认为停不住、但车其实停得住"的假紧急——你的判断已经把这一点纠正为
"问 `car.acceleration`（能不能做到问能力）"，这与 RSS 的 `b_min` 是同一个思想。

### 4.6 舒适性指标

工业界常用：**jerk ≤ 2~3 m/s³**（舒适区，紧急时放宽）、**横向加速度 ≤ 2~3 m/s²**（乘员舒适边界）、
纵向加速度分段（巡航/减速/紧急）。你的 `A_LAT_MAX` 与 `marginFor(v)` 标定表属于同一族：
`marginFor(v)` 是"按速度标定的安全/舒适侧向裕度"（你有 `docs/margin-calibration.md` 与
`js/headless/calibrate-margin.ts` 这条标定链路——**这在自学项目里相当罕见，是正确做法**）。
要补的是：把 jerk 也变成**可观测指标**（现在你统计的是收敛轮数与 `planMs`，没有 jerk/横向加速度的 p95）。

### 4.7 验证：影子模式与"每公里指标"

工业界的做法：**影子模式**（真实数据回放，只记录不接管）、**场景库**（每个场景带期望行为断言）、
**按里程统计的负向指标**（非预期制动/AEB 误触发次数每千公里、TTC 分布、jerk p95）。
你的等价物：`js/headless/run.ts` 产出归档 → `js/headless/detector.ts` + `js/headless/checks/` 四类检查 →
但**缺"按里程的负向指标"**。你为幽灵刹车临时写的那套脚本（"0.5s 内掉 >1.5m/s 且本车道前方无真障碍"）
**就是影子模式的雏形**——把它固化成 detector 的一个 check，你就有了工业界同款的回归指标。

## ⑥ 可落地的最小练习

### 练习 1：把跟驰安全门从"能不能停住"改成"能不能降到前车速度"

**背景**（你已量化）：`js/algo/plan/lead.ts` 现在的门是
`gap > (v² − v_lead²)/(2a) + 10m`，不过就**丢弃跟随目标** ⇒ 退回"停在静止障碍前"的停车线 ⇒
实测 315 个硬减速里 **60~100m 段占 101 个、>100m 占 42 个**（提前重刹）。
**做什么**：
1. 把"门不过 ⇒ 返回 null"改成"**仍然返回跟随目标**，速度目标由跟驰公式自然压下来"
   （`vTarget = min(vCap, vLead + (gap − 6m)/1.4s)`；`gap → 0` 时该式自然给出 ≤0 ⇒ 夹到 0，
   由**紧急制动层兜底**）。即：**跟驰分支负责"该减速就减速"，物理做不到才交给 emergency**。
2. 同步改 `js/test/plan/lead.test.ts` 里那两条安全门断言：从"间距不足 ⇒ 返回 null"改成
   "间距不足 ⇒ 返回的目标速度**低于**前车速度"。
3. 在 [`js/test/plan/planner-safety.test.ts`](../../js/test/plan/planner-safety.test.ts) 补一条：
   **跟驰分支不得取消必要刹车**（构造"前车骤停 + 间距不足"⇒ 仍必须有停车线/紧急剖面）。
**可量化验收（同场景同种子，G4 交通场景 `scenarios/bj-g4-dujiakan-traffic.json`）**：
- 硬减速采样点（0.5s 内掉 >1.5 m/s）**下降 ≥30%**（改动前基线：387）；
- 全程最低速 **≥5 m/s**（改动前会归零）；
- `collision_true` **仍为 0**；EMERGENCY 帧数**不增加**；
- 到达时间变化 **≤5%**；
- **反向验证**：用开关把改动关掉 → 上述指标必须回退（否则说明测量没抓住机制）。
**难度**：中等，半天。

### 练习 2：把"每公里非预期制动"做成检测器指标

**做什么**：在 `js/headless/checks/` 里新增一个 check（例如 `unnecessary_braking`），
判定函数抽成纯函数并单测：**事件定义** = 在一个 0.5s 窗口内自车速度下降 >1.5 m/s（≈3 m/s²）
**且**当时"本车道前方 `D` 米内没有任何真障碍"（`D` 可配，建议同时统计 80m 与"任意距离"两档，
因为你已经因为只看 80m 而误判过一次：那次真实的减速对象在更远处）；
输出 = **次/公里**，并写进 `report.md` 与 `summary.json`。
**可量化验收**：
1. 新增单测覆盖判定函数：构造"硬减速 + 本车道无车" → 计数 1；"硬减速 + 本车道有车" → 计数 0；
   "平缓减速" → 计数 0（三条都不能少）。
2. G4 静态巡航场景（无交通）该指标 **≈0**；G4 交通场景 **>0** 且与你的临时脚本口径一致（±5%）。
3. 同种子复跑，指标逐位可复现（你的归档保确定性，这一条必须成立）。
4. 全量测试全绿（当前 491）。
**为什么值得做**：这是你从"临时脚本排查"升级到"**工业界同款回归指标**"的一步；
以后任何改动（尤其是练习 1 与预测层）都能用它衡量"是否真的更平滑了"。
**难度**：中等，半天。

## ⑦ 常见坑与误解

- **以为"横纵解耦 = 路径算一次、速度算一次"**：它是**迭代**（你已经在做 ≤3 轮）。若只算一轮，
  高速时会出现"按上一个速度算的横移距离不够"⇒ 要么越界要么幽灵抖动。
- **把"停车线"当成安全**：对**静止**障碍它是对的；对"会走的车"它是**最坏假设**（`tMax = ∞`）。
  你观测到的"提前重刹"和"该跟不跟"都是它的直接后果。
- **用规划侧的保守常数代替车辆能力**：`A_BRAKE` 之类的保守常数会让"其实停得住"变成"假紧急"。
  正确做法问 `car.acceleration`（你已纠正 ✓），这也是 RSS 用车辆自身 `b_min/a_max` 的原因。
- **把 AEB 塞进规划器**：业界把紧急制动放在**控制层独立节点**（Autoware）或**独立守护模块**（Apollo Guardian），
  因为它必须能在"规划器本身出错/变慢"时仍然生效。你的 `EMERGENCY` 在规划器内 ⇒ 规划器一旦卡住，兜底也没了。
- **只测"到没到终点"**：到达时间只反映效率。舒适性与安全性要靠**按里程的负向指标**
  （非预期制动率、TTC、jerk p95）——你为幽灵刹车写的那套脚本已经证明了它的价值。
- **以为"责任划分"可以从几何里涌现**：你的走廊膨胀、"威胁度"排序、分级提升都试过了（见 CLAUDE.md 的 S1② 两轮记录），
  最后能修好幽灵刹车的是**修正投影 + 本体坐标系交叉校验**；"该不该让"现在有了**第一条独立规则**（中心不在我车道且没朝我动 ⇒ 阻塞带不许越界，见 [`neighbor-lane.test.ts`](../../js/test/plan/neighbor-lane.test.ts)），但**切入/压线的责任转移**仍然缺 ✗。
- **以为 LQR/MPC 一定优于 Pure Pursuit**：在 `A_LAT_MAX` 与你的速度域（≤35 m/s）下纯跟踪够用；
  MPC 的收益在极限工况与多约束耦合处。**先补"预测层与责任规则"，再谈换控制器**。
- **以为博弈/POMDP 是必需品**：多数量产栈是**规则 + 状态机 + 安全包络**（RSS 就是规则的极致形式）。
  POMDP 类方法在"人类交互密集"的场景才划算，代价是可解释性差、验证困难。
- **忘了"上一帧"**：Apollo 的 ST 代价里显式含"与上一帧剖面之差"（正则化），
  你的 `speed.ts` 没有 ⇒ 相邻帧的目标速度可以完全不同。这与你统计的 `state_flapping` 直接相关。
- **把标定表当成"调参"**：`marginFor(v)` 有独立的标定链路（`calibrate-margin.ts` + `docs/margin-calibration.md`）
  与实测下界（舒适裕度取 `max(1.5m, p95)`），这比"手动调一个数"专业得多——**继续这么做**，
  并且把每次改动都写成"标定 → A/B → 反向验证"三段。
