## ① 这套东西解决什么问题

你现在的规划器把**每个障碍当成静止矩形**（[`js/algo/plan/speed.ts`](../../js/algo/plan/speed.ts) 里的
`STObstacle { sMin, sMax, tMin, tMax }`，`tMin` 永远是 0）。后果你已经实测到了：

- 车流一密就**爬行**（前方 60m 有辆跑 15m/s 的车，你会按"停在它屁股后面"去规划）；
- `EMERGENCY` 与**走走停停**（state_flapping）大量出现；
- 正因为"障碍不会动"，跟驰只能靠 [`js/algo/plan/lead.ts`](../../js/algo/plan/lead.ts) 做**稳态跟随**，
  一旦"该跟的车在 60m 外"就被安全门丢掉、退回停车线 ⇒ **提前重刹**。

**运动预测（motion forecasting / trajectory prediction）** 就是补这一环：给每个物体
"它接下来 3~6 秒可能在哪"，把 **静态矩形** 换成 **随时间的占用（occupancy over time）**。
它在业界流水线里的位置是固定的：

```
传感器 → 检测 → 多目标跟踪(MOT) → ★预测★ → 行为决策 → 运动规划 → 控制
                  ↑ 你已经做到         ↑ 本文         ↑ 你的 SL/ST 解耦
                    objects.ts        缺这一环         paths.ts / speed.ts
```

一句话：**跟踪给你"它现在在哪、多快"，预测给你"它等会儿在哪"。规划器必须消费后者。**

## ④ 关键机制 / 公式 / 指标

### 4.1 任务形式化

- 输入：**历史** $X = \{x_{-T_{obs}+1}, \dots, x_0\}$（每个 $x$ 含位置、朝向、速度、类别）
  ＋ **地图** $M$（车道中心线、可行驶区域、路口拓扑；本仓库对应 [`frenet.ts`](../../js/algo/plan/frenet.ts)
  的参考线与 `laneCenters`）。
- 输出：$K$ 条未来轨迹 $\{\hat Y_k, p_k\}_{k=1..K}$，$\sum_k p_k = 1$。

> 各数据集的 T_obs / T_pred、采样率、被评分 actor 的定义**都不一样**，别背数字，
> 用之前去对应论文/开发包确认。（本文核实过的两条：Argoverse 1 每个场景共 **5 秒**；
> WOMD 是 **10 万+ 场景、每个 20 秒 @10Hz** —— 都出自各自论文摘要。）

### 4.2 三个可以几小时写完的基线（**对本仓库足够**）

1. **CV（恒定速度）**：$\hat p(t) = p_0 + v_0 t$。
   你的 `ObjectTrack` 已经有 $(s, l, v_S, v_L)$，所以**在 Frenet 里做 CV 是 5 行代码**：
   $s(t) = s_0 + v_S t$，$l(t) = l_0 + v_L t$。
2. **CTRV（恒定转率 + 恒定速度）**：状态 $(x, y, v, \psi, \omega)$，解析递推
   （$\omega \to 0$ 时退化为直线）：

   $$
   x_{t+1} = x_t + \frac{v}{\omega}\big[\sin(\psi_t + \omega \Delta t) - \sin\psi_t\big],\quad
   y_{t+1} = y_t + \frac{v}{\omega}\big[-\cos(\psi_t + \omega \Delta t) + \cos\psi_t\big],\quad
   \psi_{t+1} = \psi_t + \omega\Delta t
   $$

   **CTRA** 再加速度 $a$（纵向），精确解含 Fresnel 积分，工程上常用一阶近似。
3. **车道跟随（lane-following）**：在 Frenet 里就是 $\hat s(t) = s_0 + v_S t$、$\hat l(t) = l_0$
   （横向保持不变）——横坐标不动，纵向按速度前进。**它编码了"车只能沿车道走"这个先验**，
   在结构化的高速/快速路上，效果远超它的复杂度。
   （注意：`l` 不变 **不等于** 车走直线——参考线自己就是弯的，`l` 不变 = 沿车道中心走。）

> **为什么"CV + 车道跟随"就够你用了**：你要解决的不是"预测行人过马路"，
> 而是"前方那辆车 2 秒后还在不在我车道上、以什么速度"。这个问题的答案 95% 由
> **它当前所在车道 + 当前速度**决定。CTRV/LaneGCN 是后面的事。

### 4.3 评测指标（务必分清"min-over-K"）

设第 $n$ 个场景真值终点/整条轨迹为 $Y^{(n)}$，第 $k$ 条假设为 $\hat Y_k^{(n)}$：

$$
\mathrm{ADE}_k = \frac{1}{T}\sum_{t=1}^{T}\big\|\hat Y_k(t) - Y(t)\big\|_2,\qquad
\mathrm{FDE}_k = \big\|\hat Y_k(T) - Y(T)\big\|_2
$$

$$
\mathrm{minADE}_K = \frac{1}{N}\sum_n \min_{k\le K}\mathrm{ADE}_k^{(n)},\qquad
\mathrm{minFDE}_K = \frac{1}{N}\sum_n \min_{k\le K}\mathrm{FDE}_k^{(n)}
$$

- **Miss Rate（MR）**：$K$ 条假设**没有任何一条**的终点落在真值终点 2m 内的场景比例
  （即 $\min_k \mathrm{FDE}_k \ge 2\text{m}$）。
- **brier-minFDE**：$\mathrm{minFDE} + (1-p^{\ast})^{2}$，其中 $p^{\ast}$ 是**FDE 最小那条**的概率。
  直觉：**"蒙对了"也要罚**——如果你把正确那条的概率给得很低，说明模型并不知道自己对。

**为什么必须 min-over-K**：多模态任务的本质是"一条对就算对"。
但只用 min 会奖励"撒 6 条互不相同的轨迹、概率乱给" ⇒ 所以业界都配一个概率项
（brier / NLL）和 MR。

**指标的直觉对照**

| 指标 | 关心什么 | 什么时候会骗你 |
|---|---|---|
| minADE | 整条轨迹平均贴合度 | 只报一条特别长的假设也能刷低 |
| minFDE | **终点**对不对（规划最关心） | 终点对、中途穿墙也可能高分 |
| MR | "全军覆没"的比例 | 数据里全是直行时会显得很好 |
| brier-minFDE | 概率给得对不对 | 需要模型输出校准过的概率 |

### 4.4 SOTA 的三条主线（只需知道思路）

- **矢量化 + 图神经网络**：VectorNet（局部子图 → 全局交互）、LaneGCN（车道图卷积 + 沿车道膨胀）。
- **Transformer + 分层/等变**：HiVT、QCNet（旋转不变/等变、query 中心，编码一次多次查询）。
- **联合/交互预测**：WOMD 提倡的 joint prediction、INTERACTION 的博弈场景。

共同点只有一句：**把地图与"物体只能沿车道走"的先验吃进去**。你的参考线已经具备这个先验的原料。

**做什么**
1. 在 [`js/algo/objects.ts`](../../js/algo/objects.ts) 加纯函数
   `predictTrack(t, horizon, model: 'cv' | 'ctrv')`，返回未来若干采样点（Frenet 或笛卡尔都行，但要一致）。
2. 新建 `js/test/algo/predict.test.ts`：构造"匀速"与"匀速转弯"两条合成轨迹，
   断言 1s 后的预测位置误差。
3. 用一个脚本（或在现有 headless 流程里）跑
   `npm run sim -- --scenario scenarios/bj-g4-dujiakan-traffic.json`，
   把**跟踪出的轨迹**与归档里的 `traffic` 真值逐帧配对，统计 **1s 预测的 FDE 分布（p50/p90）**。

**验收判据（可量化）**
- 合成匀速轨迹：CV 的 1s FDE 中位数 **< 0.1m**（否则就是坐标/单位写错了）；
- 合成转弯轨迹：CTRV 的 1s FDE **明显小于 CV**（把两个数写进测试注释）；
- 真值场景：CV 的 1s FDE **p50 < 1.0m**、p90 < 2.5m（配对规则可以先宽松：按 $(s,l)$ 最近邻配对，
  距离 > 3m 视为配对失败并计入报告）；
- 运行 `npm test` 全绿（不许为了新测试改旧断言）。

### 练习 2（3~4 小时）：把 ST 层的"静态矩形"改成"斜条带"

**做什么**：在 [`js/algo/plan/planner.ts`](../../js/algo/plan/planner.ts) 构造 `STObstacle` 时，
对本车道前方**会动的**物体（`|vS| > 1.5 m/s`，即你在 `inLaneGapAhead` / `selectFollowTarget` 里
已经筛过的那批），用 CV 预测把它的占用写成
`tMin = (sMin - s_ego)/v_ego` 之类的**到达时间**（或直接给 `tMin/tMax` 一段斜坡），
而不是 `tMin = 0`。

**验收判据（同种子 A/B，用 `runs/` 的 summary/issues 对比）**
| 指标 | 要求 |
|---|---|
| 碰撞 | 保持 **0**（这是硬门槛，任何新增碰撞都算失败） |
| `EMERGENCY` 帧数 | 下降（哪怕 10% 也算成功） |
| 硬减速（0.5s 掉 >1.5m/s）采样点数 | 下降 |
| 到达时间 | 不劣化 > 2% |
| 静态场景 | 黄金基线（径向图）**逐位不变**（因为那里没有"会动的物体"） |

> 提示：先只改"本车道 + 前方 + 会动"的那一类物体，**不要**一次性改所有障碍 ✗。
> 你的仓库里已经有过教训：一次改太多判据 ⇒ 安全回归测试成片失败。

## ⑦ 常见坑与误解

1. **"预测不准所以别用"** ✗ —— 预测本来就是概率性的，规划器要做的是**对误差鲁棒**
   （留裕度、按概率加权），而不是要求预测准。你现在的"静态假设"是最保守的一种预测（$v\equiv 0$），
   它的代价是**把会走的车当成墙**（这就是你 EMERGENCY 的来源之一）。
2. **单模态输出** ✗ —— 只给一条未来，规划器会被自己的预测骗（前车"一定直行"⇒ 不敢超车也不让行）。
   要么给 K 条 + 概率，要么至少给出**不确定度**（见 05 的协方差）。
3. **用真值调算法** ✗ —— 评测可以用真值，**决策回路不许**。你在
   [`js/algo/objects.ts`](../../js/algo/objects.ts) 里守的"规划器只信 LiDAR"是对的，
   预测层也必须只用 LiDAR/跟踪输出。
4. **只报 minADE** ✗ —— minFDE 才是规划最关心的（终点错 = 撞上）；两者一起报。
5. **忽略坐标系与参考线误差** ✗ —— 你的"幽灵刹车"根因就是投影误差（远处 ~1m）。
   预测是在同一套 Frenet 里做的 ⇒ **投影修不准，预测也会偏**，而且偏差会被速度放大。
6. **预测出"开出路面"的轨迹** ✗ —— 没有车道约束的 CV 会这么干。
   工程做法：预测后**投影回车道**（或直接在 Frenet 里预测 + 用 `laneCenters` 限制 $l$ 的范围）。
7. **忘了"怎么消费"** ✗ —— 预测不是拿来看的。落点一定在**规划器**：
   ST 条目填时间维（本文练习 2）、行为决策用"它将来占哪条车道"（超车责任划分）。
8. **过度追求 SOTA 模型** ✗ —— 你先需要的是"会动的矩形"，不是 LaneGCN。
   本仓库是学习模拟器：**CV + 车道跟随 + 一个 ADE/FDE 指标** 就已经把最大的代差补上了。
