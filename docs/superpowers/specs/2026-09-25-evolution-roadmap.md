项目已经"能跑通全链路、能用批量数据做根因定位"；接下来的演进不是继续调参，而是补三块地基——**可信的度量**（评测面与基线）、**结构性的算法**（优化化、纵向、安全仲裁）、**可见性**（把走廊/代价/状态画出来）；更远的保真度（障碍实体、动态障碍、动力学）是解锁新能力的前置钥匙。

### 1.4 结构性观察（本次分析新增）

1. **`js/sim/engine.ts:207-224` 藏着一个硬编码紧急制动**（前方 LiDAR < 5m 且 v > 3m/s → 减 5m/s²、下限 2m/s），在控制订阅者内直接改速度、绕过规划器——正是 P2 教训（执行层隐式覆盖规划意图）的复发形态。
2. **最新的算法表示在界面上不可见**：`env/renderer/overlays.ts` 只画射线/轨迹/路线/GPS 环；走廊、候选、代价、贴边惩罚、紧间隙状态一概没有。

## 2. 不变量与纪律（所有方向共用）

**不变量**：`Trajectory` 输出契约；ST 接口（`STObstacle`/`SpeedMode`）；传感器驱动（算法只吃 LiDAR 命中，禁止障碍物真值）；同种子逐帧确定性；量纲以 `m()/mps()` 书写；`env`/`algo` 严格分离；中文注释（`algo/` 必须有原理与参数依据）。

**纪律**：一方向一循环（spec → plan → TDD → 批量 A/B → 负结果入库）；单变量实验；指标**成对读**（P11：碰撞段数/帧数、零碰撞与到达率、用时与进度）；上一方向验收通过再启动强依赖它的下一方向；批量劣化即回滚并记录负结果。

**门禁原则（本路线图建议升级）**：从"10 场景布尔"升级为"场景族 × N 种子 + 分布指标"，见 E1。

## 3. 演进方向

命名：`R`=收口/工程，`E`=评测，`A`=算法，`S`=仿真保真，`V`=可视化/学习体验，`X`=长期架构。规模粗估：S ≤0.5 天、M 1–2 天、L 3–5 天（含测试与批量验证）。

### 波次 0：收口（前置，不属"演进"但 blocking）

#### R1 走廊 A+B 收口（M）
- **范围**：迁移 `paths.test` / `planner-safety.test` 的断言（A3 Step 4 迁移清单）；重取引擎黄金基线（人工核验数值合理性）；跑 B4 批量门禁（0/0 不劣化、到达 ≥8/10、用时/进度不劣化）；刷新标定覆盖率 ≥95%；同步 `CLAUDE.md` 规划器章节 + spec 附录 B 执行记录。
- **交付**：一份 A/B 对比表；要么通过门禁，要么按 spec §6 纪律回滚接线并把负结果入库。
- **风险**：A 单独接线已两次失败（候选丢失 / 执行跟不上）；B 的裕度表偏保守（低速 1.15m）可能把"慢行可过"判成封死 → 到达率下降正是启动 A1（阶段 C）的判据。

#### R2 测试脚本与工具链锁定（S）
- **范围**：`npm test` 改为在当前 Node 可用的形式（glob 或 `--test` 无参 + 默认匹配）；`package.json` 加 `engines`（或 `.nvmrc`）；在 `CLAUDE.md` 记录 Node 版本要求。
- **验收**：全新克隆下 `npm test` 一次通过（除已知红）。

#### R3 CI 门禁（M）
- **范围**：CI 跑 `tsc --noEmit` + 单测 + 种子批量，(a) 输出聚合报告，(b) 按门禁阈值退出非零。把当前手工 `for` 循环 + `node -e` 聚合脚本化为一个 headless 子命令（如 `js/headless/batch.ts`）。
- **交付**：`batch.ts`（跑场景集 + 聚合 + 门禁断言 + 退出码）——它同时是 E1/E2 的载体。

### 波次 1：可信的度量（战略优先级最高）

#### E1 评测面扩容（L）
- **动机（证据）**：见 §1.4-3。现有 10 场景不足以支撑结构改动的成败判定；且项目调参已进入收益递减（`ISSUE_HISTORY` 第七/八轮结论）。
- **范围**：
  1. 场景族划分（直线避障 / 窄口 / 急弯 / 多障碍序列 / 贴边 / 死口袋），每族给出**参数化生成器**（固定种子 → 同族不同难度）；
  2. 种子矩阵：族 × 30~100 种子（headless 分钟级可完成，需实测单场景耗时）；
  3. 场景**可解性检查**（P9 教训自动化）：出生区净空、初始速度 vs 制动距离、是否存在几何可行线——不可解样本标记为 `unsolvable` 而非计入失败。
- **交付**：`scenarios/families/*.json`（或生成器）+ `batch.ts` 的矩阵模式 + 分布报告。
- **验收**：同一种子矩阵两次运行结果逐字节一致（确定性保持）；报告含每族样本量与不可解率。

#### E2 基线库 + 逐帧 diff 工具（M）
- **动机**：现在基线是文档里手抄的数字；确定性（本项目最强的方法论武器）尚未工具化。
- **范围**：
  1. `runs/baselines/<tag>.json` 快照（版本化、含 git commit 与 Node 版本）+ 对比 CLI（指标差 + 回归清单 + 阈值判定）；
  2. `diff` 子命令：同场景同种子两次运行 → **首个分歧帧**（比较 records 流），输出该帧两边的 plan/step 记录 diff。
- **验收**：对一个已知回归（如 R1 回滚前）能自动定位到首个分歧帧并打印差异字段。

#### E3 指标扩展 + 报告三件套（M）
- **范围**：新增舒适度（横向加速度 / jerk 分布）、安全裕度分布（min gap 直方图与 p05）、规划单轮耗时与（阶段 C 后的）收敛轮数、紧急制动次数与持续时间、状态切换计数；把 P11 的"段数/帧数/到达率"固定进 `report.md` 头部（已在遗留清单）。
- **验收**：`report.md` 固定段落存在且字段可被 E2 的对比器读取；新增字段进 `summary.json`（注意归档 schema 兼容，见 E4）。

#### E4 归档 schema 版本化（S）
- **范围**：`shared/types/interfaces/archive.ts` 加 `schemaVersion`；旧归档回放时走字段降级/迁移（现已出现 `tight` 等新增可选字段）。
- **验收**：旧 `.run.json` 仍可导入回放不崩。

### 波次 2：算法纵深

#### A1 阶段 C：路径-速度迭代收敛（L）
- **动机**：窄口通过性本质依赖速度（发展段随 v² 缩放），顺序单轮传递丢反馈 → 停车后死锁（v=0 时唯一可行速度被自己的参数化封锁）。spec `2026-09-25-corridor-planner-evolution-design.md` §5 已设计（EM 风格交替，最多 3 轮 + 确定性兜底）。
- **依据（新）**：B 的标定证明横向误差**随速度下降**（低速 1.15m / 高速 0.60m），裕度表必然偏保守 → "敢不敢试紧线"只能由路径-速度联合决定。
- **验收**（spec §5.3）：hairpin-s8 类窄口不再死锁——要么干净通过、要么干净停车，**不得引入接触**；批量到达率与用时/进度不劣化；新增"需 >1 轮的帧占比"与单帧规划耗时指标。
- **依赖**：R1（A+B 门禁通过）、E3（指标位）。

#### A2 走廊内连续优化（QP）（L）
- **动机**：从"7 个离散候选 + 排名"跃迁到"走廊内一次解出光滑 l(s)"；贴边/曲率/舒适度代价连续化，消除候选打不中缝隙与档位跳变两类结构问题（spec 已把 QP 列为将来独立演进）。
- **范围**：走廊（A 的 `corridor.ts`）作为硬约束；目标函数 = 中心偏离 + 曲率 + 贴边 + 切换平滑；离散化后用小型 QP/带约束最小二乘求解。
- **风险与缓解**：无现成 QP 依赖（纯 TS 手写或引库需权衡）；**确定性**与性能（15Hz 预算 <5ms）必须进单测/归档指标；若不稳定，保留"QP 失败 → 回退离散候选"的降级路径。
- **验收**：同批次 0/0 不劣化；路径曲率与贴边指标下降；单轮耗时进报告。

#### A3 纵向升级（IDM / jerk 约束 / ST-QP）（M–L）
- **动机**：`speed.ts` 只有 cruise / stop（停车线）/ emergency 三档，无法表达"跟车"与"舒适"。
- **范围**：先做**跟车（IDM 或前车距离-速度剖面）**——为 S2 的动态障碍做准备；再做 jerk 约束的平滑剖面。
- **验收**：剖面满足加加速度上限（单测）；跟车场景下不追尾、不振荡（新场景族）。

#### A4 显式纵向安全仲裁（S–M）
- **动机**：`engine.ts:207-224` 的硬编码紧急制动绕过规划器直接改速度（P2 教训复发），不可测、不可解释、与规划意图可能矛盾。
- **范围**：抽为显式模块（如 `algo/safety.ts`）：输入 = LiDAR 前方距离 / 速度 / 规划意图，输出 = 允许的速度上限或制动覆盖，并**发布 sim:event**（可归档、可检测、可解释）。安全性原则参考 RSS（安全距离 = 反应距离 + 制动距离）。
- **验收**：紧急制动事件在归档中可追踪且携带触发原因；原硬编码路径删除；批量 0/0 不劣化。
- **注意**：这是**接口语义变更**（安全边界从"engine 兜底"变为"显式仲裁"），需单独 spec 并单变量验证。

### 波次 3：仿真保真（解锁新能力）

#### S1 障碍物实体化（P10）（M–L）
- **动机**：障碍对物理模型完全透明，导致①观测混淆（真缺陷与常态"穿过"难分辨）②停死不可恢复③评测帧数被停留放大。
- **范围**：MTV 推出 + 法向速度清除（`ISSUE_HISTORY` 备选①，推荐）；碰撞事件归档；明确评测语义（接触后继续 vs 终止）——此项**改变评测语义**，必须单独 spec + 重取全部基线。
- **验收**：车不再穿模；接触后能停住且不抖动；新旧批量结果按"语义变化"逐项复核。

#### S2 动态障碍 + 多帧跟踪（L）
- **动机**：`perception.ts` 只导出 `sense()`，输出逐射线距离数组——单帧无速度、无目标。这是"感知"这一课真正缺失的部分，也是"提交窗口/晚承诺"显现实义的前提（静态场景下"交互"不存在）。
- **范围**：①射线聚类（连通域 / DBSCAN）→ 目标框与质心；②多帧关联 + 卡尔曼（位置/速度）；③预测（恒速/恒转弯）→ 规划器消费"预测轨迹"而非瞬时命中；④LiDAR 加噪与遮挡处理。
- **验收**：目标速度估计误差分布；动态场景族下无追尾/无碰撞；感知检测器（幻影/漏检）指标不劣化。
- **依赖**：A3（跟车）与传感器驱动原则不变（仍只吃命中，不吃真值）。

#### S3 控制升级（M）
- **动机**：现在 Pure Pursuit + 标量油门；"终点速度"这一个数字承载了整条速度剖面（P2 的接口层教训仍在）。
- **范围**：横向 Stanley 或 MPC 对照；纵向用规划剖面的**采样时间维**（而非标量）；执行器一阶滞后与转向角速率限制。
- **验收**：横向误差 RMSE、曲率跟随误差、执行饱和时长进指标；同批次不劣化。

#### S4 车辆动力学（M–L，可选）
- 运动学自行车 → 动力学（轮胎侧偏/不足转向）。用于回答"规划出的轨迹为什么执行不了"，并给 S3 提供真实的被控对象。
- **验收**：存在一个"运动学可行但动力学超出附着极限"的场景，且规划器能通过受限裕度识别它（与 A2 的裕度联动）。

### 波次 4：可见性与学习体验（投入产出比最高）

#### V1 规划器内省可视化（M）
- **动机**：§1.4-2——最新算法表示完全不可见。调试与学习双重收益。
- **范围**：3D 场景覆盖层绘制 ①双/三走廊自由区间（舒适/物理/迟滞带）②候选路径（按 cost 着色，best 高亮）③贴边惩罚热点 ④`TightState` 与 `margin(v)` 状态文本/HUD ⑤（A2 后）QP 解与约束活跃集。
- **验收**：开启覆盖层不影响仿真确定性（渲染只读 `debug` 对象）；三张截图入文档。

#### V2 遥测曲线面板（M）
- **范围**：v(t)、a(t)、δ(t)、横向误差、min gap、规划耗时、状态机时间线；与回放游标联动，点击曲线跳帧。
- **验收**：回放任意 `runs/<id>` 可出图；与 `frames.jsonl` 数值逐点一致（单测）。

#### V3 A/B 双运行对比视图（M）
- **动机**：单变量实验纪律目前靠人肉。与 E2 的 diff CLI 共享数据层。
- **范围**：两条轨迹叠加 + 指标表 + 首个分歧帧跳转。
- **验收**：能直接对比 R1 回滚前后的两组归档。

#### V4 场景编辑器 + 参数实时面板（M–L）
- **范围**：画布上放置/拖动障碍、设起终点与初速 → 导出 `scenarios/*.json`（并登记 `index.json`）；侧栏实时调 `CLEAR` / `marginFor` / 迟滞带 / 代价权重并即时重规划（仅调试模式，不写回源码）。
- **验收**：编辑器导出的场景在 headless 下与原手写 JSON 同源可跑；参数面板调参不破坏确定性（仅当显式改参数时行为变化）。

### 波次 5：长期架构

#### X1 时延与异步仿真（L）
- **动机**：`MessageBus` 是进程内**同步** pub/sub——真实的 ROS 世界里，通信有时延、有丢帧、有节点崩溃。"15Hz 规划 + 60Hz 控制"这一设计从未在延迟下被压测。
- **范围**：可选的消息延迟/抖动/丢弃注入；订阅者隔离（Worker）可选；时钟与时间戳语义（感知时间 vs 决策时间 vs 执行时间）。
- **验收**：时延注入下给出鲁棒性曲线（延迟 vs 碰撞/到达）；确定性在"无注入"下保持。

#### X2 多智能体（L）
同进程跑多车各自管线，练调度、资源竞争与交互（与 S2 的预测/博弈合流）。

#### X3 状态估计（M）
GPS 目前只是加噪（σ=1.25m，10Hz）。加 EKF（IMU + 轮速 + GPS），把"定位"从 `env/localization.ts` 的噪声源升级为真正的估计问题——经典必修课，且与 P6（地图假设错误）形成对照。

## 6. 开放问题

1. **评测成本的量级**：单场景 headless 耗时未量化。E1 的种子数（30？100？）取决于此，需先实测再定矩阵规模。
2. **`margin.ts` 与标定报告的权威版本**：三者不一致（§1.3），需确认"低速 1.15m 保守表"是否为最终意图；若是，B 的到达率代价可能触发 A1 的必要性论证。
3. **S1 的评测语义**：接触后"继续仿真"还是"终止 episode"？前者保留数据但污染帧数统计，后者干净但截断归档——需用户决策后单独 spec。
4. **A2 的 QP 实现载体**：纯 TS 手写（可控、无依赖、需自己保证数值稳定）vs 引入小型求解器（快、需评估确定性与包体）——需在设计 A2 时定夺。
5. **可视化与确定性的边界**：V1/V4 只读 `debug`、不进入仿真路径，需在实现时以测试固化（渲染层不得影响 `frames.jsonl`）。
6. **是否需要"能力边界"正式声明**：oval-s8 / hairpin-s8 这两个停车场景是"诚实停车"（已验证 0 碰撞）还是待攻克缺陷？建议在 R1 后的文档里明确写死结论，避免后续反复返工。
